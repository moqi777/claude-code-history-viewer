## 2. 有笔记的会话排到前面

问题复现（leader 的例子，真实库，只读）：搜"电池 耗电"，0.4.0 的 `notes` 第 1 条是"笔记本电池掉电过快"那个会话（`a3dc8377`）的笔记，但这个会话不在 `results` 里（它的消息里没有同时出现两个词）；`results` 第 1 名是 WindowServer 的长会话，"找出耗电大户"第 5。

**改动（`search.rs`）**
1. **笔记命中的会话并进 `results` 并排在前面**（`promote_note_sessions`）：按笔记的顺序先放这些会话，再放其他会话；同一个会话只出现一次（消息也命中的，带着它的消息命中一起挪到前面）；没有消息命中的会话作为"只有笔记"的一条加进来（`hits` 为空，`hit_messages` 0，`has_note` true，`resume`/`paths` 齐全），`matched_sessions` 相应加上。`--notes 0`（关掉笔记）时顺序回到只看消息。
   **只有"笔记含有查询的每个词"（严格匹配）才提前。** 我第一次做成了"只要有笔记命中就提前"，在真实库上 15 道题的前 3 命中从 14 掉到 13（宽松匹配的笔记会把不相关的会话顶到最前面，例如 `01a09ea0` 出现在好几道题的前两名）。笔记搜索本来就是先严格、严格没有才宽松，现在把"是不是宽松"带出来，宽松的笔记不改排序。
2. **标题命中加分**（`title_factor`，`TITLE_BOOST = 0.5`）：会话标题里含有查询词，分数乘 `1 + 0.5 × 命中比例`（所有词都在标题里最多 ×1.5）。减轻长会话靠重复出现排到前面的问题。
3. **默认输出里保留 `has_note`**：它本来就在默认输出里（只在为 true 时才有这个键，所以搜不到笔记时看不到）；现在加了断言，`agent_json(.., false)` 里有笔记的会话有 `has_note: true`，没有笔记的会话没有这个键。

**测试（`sync.rs`、`search.rs`）**：
- `the_session_of_a_matching_note_comes_first_even_without_a_matching_message`：笔记会话在前、没有消息命中；`matched_sessions`=2；`rank` 连续；默认 JSON 里 `has_note`；`--notes 0` 退回消息顺序
- `a_session_with_both_a_note_and_message_hits_is_listed_once_with_its_hits`
- `a_loosely_matching_note_does_not_push_the_message_hits_down`
- `a_note_found_only_by_its_keywords_is_returned_even_when_no_message_matches`（改过：现在 `results` 里有这个会话，没有消息命中）
- `a_title_with_the_query_words_raises_the_score_by_how_many_it_has`

**前后对比（真实库，只读）**：`docs/agent-kb/p4-evidence/rank_eval.py` 对 `P3-eval.md` 的 15 道关键词题 + "电池 耗电"，记录期望会话在 `results` 里的名次。"之前"用 `/Applications` 里的 0.4.0，"之后"用 0.4.1 的构建；输出在 `p4.1-evidence/rank-before.txt`、`rank-after.txt`。

逐题：
- **"电池 耗电"**：之前 `a3dc8377` 不在 `results` 里（0 名）→ 现在**第 1**。完整排序前后：

  | 名次 | 之前 | 之后 |
  |---|---|---|
  | 1 | WindowServer 长会话 `019f69f8`（33.5） | **笔记本电池掉电过快 `a3dc8377`（有笔记，无消息命中）** |
  | 2 | 为什么我的 mac 现在这么烫 `01a0ccf1`（28.0） | `019f69f8` |
  | 3 | 本地 Agent 历史会话知识库 `c4c081c6`（25.5） | `01a0ccf1` |
  | 4 | 地图选点进阶功能 `15bf7c02`（22.2） | `c4c081c6` |
  | 5 | 找出耗电大户 `019f49ee`（18.1） | 找出耗电大户 `019f49ee`（22.6） |

  （`15bf7c02` 本来就和耗电无关，只是它有笔记，之前排在第 4。"找出耗电大户"因为标题命中，分数从 18.1 涨到 22.6，但仍在第 5；要求的是 `a3dc8377` 进前 3，已达到。）
- `fastjson 升级 空指针`：之前不在前 5（0 名）→ 第 2（标题加分的作用）。
- 其余 14 题名次不变或更靠前（`502 网关` 2→1，`dubbo provider RpcException` 2→1，`Ghostty…` 1→1 等）；**唯一变差的一题**：`tedis 依赖` 1→2，因为另一个会话 `01a09ea0` 有一条同时含这两个词的笔记，按规则排在前面。
- 去掉标题加分单独跑一遍（临时把 `TITLE_BOOST` 改成 0）：前 5 / 前 3 都是 15/16，也就是标题加分多救回了 1 题（`fastjson…`）。

**注意点**
- "只有笔记"的会话的 `score` 用的是笔记的分数，和消息分数不在同一个尺度上，所以 `results` 的 `score` 不再严格从大到小（`rank` 是连续的，按展示顺序）。上面"电池 耗电"的第 1 名分数 16.6，比第 2 名 33.5 小就是这个原因。
- skill 模板没有改（改了会让用户的 skill 变成"过期"、要再点一次更新）。老的 skill 读 `results[].session`、`resume`、`hits`；"只有笔记"的会话 `hits` 是空数组，不会出错，只是少了片段，笔记的内容在 `notes` 里。要不要在 skill 里加一句"`has_note` 为 true 而 `hits` 为空，表示靠笔记找到的"，由你们定。
- 调试版 `--kb-search` 约 0.09–0.11 s（第一次冷缓存 0.92 s），和 0.4.0 相同。
