## 4. 为什么失败没消失，重试也不运行

代码位置以下均相对于本次基线。

1. **失败端点包含全部消息。** `digest/mod.rs:465` 的 `newest_seq` 无 kind 过滤。最终失败路径（如 `mod.rs:640`）将其传给 `store::mark_failed`，记录到失败 item 的 `seq_to`。本例分别为 67、151、191。
2. **成功游标只到最后一条被输入的消息。** `input.rs:137` 的 `load_items` 只读取四种可输入类型；`next_chunk`（`input.rs:313`）的 `to_seq` 来自这些消息。`mod.rs:871` 把它写入笔记的 `digested_through_seq`，再经 `notes::index_file` 写入数据库，得到 66、150、188。
3. **新成功不会改写旧失败历史。** `store.rs:271` 的 `mark_done` 使用 `WHERE round_id=? AND source=? AND session_id=?`，只更新当前轮次 item。旧 failed 留存是现有历史记录机制；应由当前失败列表正确过滤已解决项，不能以“历史行还在”推断仍未成功。
4. **当前失败列表的过滤比较了两种不同含义的序号。** `store.rs:405` 的 `failures` 条件相当于：

   ```text
   item.state == failed
   && item.seq_to > digest_sessions.digested_seq
   && item.seq_to >= MAX(全部 messages.seq)
   ```

   这三项分别满足 `67 > 66 && 67 >= 67`、`151 > 150 && 151 >= 151`、`191 > 188 && 191 >= 191`，因而再次被 `status.rs:174` 放入 `StatusReport.failures`。
5. **重试在启动进程前被挡住。** `commands.rs:125` 的 `session_blocker` 读取整理游标并调用 `next_chunk`；该函数在可输入消息为空时立即返回 `None`（`input.rs:322`）。本次只读查询证实三个会话的这种消息均为 0，因此确定会走该分支，无须调用真实 AI 来验证。`commands.rs:102` 返回 `RunStarted::Nothing`，不会走后面的 `spawn_background`。
6. **前端有刷新，但仍收到错误的当前失败列表。** `useKbStore.ts:360` 的 `runDigest` 在返回后已经调用 `refreshDigest()`；`KbDigestCard.tsx:286` 对 `nothing` 直接 toast 英文 message，不关闭失败弹窗。单加刷新或改 toast 无法修复后端列表。

本次没有为了“验证重试”调用 GUI/CLI；以上是只读数据、查询和代码控制流的对应关系。对这三个会话而言，`next_chunk` 没有判断错误，错在失败状态展示与输入范围不一致。

## 5. 建议修法（本次未实施）

### 5.1 优先修当前失败的判断，兼容现有历史行

- 把“当前仍未解决的失败”与“过去某一轮失败过”区分开。保留旧 round/item 的真实历史，不批量删除旧 failed，也不把旧失败轮次伪改成 done。
- 为失败展示计算一个**可输入消息范围内的失败端点**：在该会话 `seq <= 旧 item.seq_to` 的记录中，按与 `input::load_items` 相同的 kind 集合取最大 seq。对本例得到 66、150、188；现有笔记游标已经覆盖它们，应从当前失败列表移除，历史仍可查看。
- 这应在读取状态时兼容旧数据，不能只改以后写入的失败端点，否则现有 3 条不会消失。以本次只读元数据代入上述条件，3 条都已解决，旧 20 项中无未覆盖的可输入失败范围。
- 判断要根据失败范围是否被持久化的整理进度覆盖，不能仅凭“有任意一个后续 done”或 `status=notes` 就隐藏失败：长会话可能只成功前几块，后面仍有真实失败。没有笔记、缺会话、时间未到等情况要分别处理，不能一律当作成功。
- 将输入类型/边界判断提取为共享规则，优先查询 kind/seq/ts 等元数据，避免状态轮询每次读取所有正文。截止时间、偏移、小数秒及子会话策略仍应与现有输入规则一致。本例的直接证据是四类输入数量为零，不依赖时间近似。
- 同时复核 `store::is_held`（`store.rs:432`）和候选筛选中“是否有新内容”的比较口径。当前失败记录和候选都使用全部消息的最大 seq；只改一边可能让自动重试抑制逻辑不一致。不要直接全局替换 `newest_seq` 或强行把 `digested_seq` 改到所有原始消息末尾，以免改变其他端点语义和截止边界。

**不需要为解决这三条展示问题重跑 AI，也不需要修改正式库或重新整理历史会话。** 正确的兼容过滤上线后，下次状态读取即可隐藏已解决项。

### 5.2 补充用户能理解的提示

- 保留“无新内容时不调用 AI”的保护。建议返回结构化原因，例如“已整理且无新内容”“没有可整理消息”“会话不在索引”，由前端本地化。
- 对本例显示“这个会话已经整理完成，没有新内容”，可提供“查看笔记”。只有后端确认属于已解决的旧失败，才从当前失败视图移除。
- 现有前端已刷新状态；核心修复应在后端。无需增加绕过 `session_blocker` 的“强制重试”来消耗额度。

### 5.3 建议回归用例

全部使用临时 HOME/数据库和模拟 AI，Mac、Windows 共用的 digest 逻辑都要验证：

1. 失败时末尾有 1 个和 3 个 `tool_result`，随后成功处理全部可输入消息：历史 failed 保留，当前失败数归零，`next_chunk=None`，重试不启动模型。
2. 当前真实数据对应的边界 66/67、150/151、188/191，笔记文件、索引和 history 一致时，应视为已解决。
3. 后续成功只覆盖前一块，旧失败范围内仍有可输入消息：仍显示真实未解决失败，允许重试。
4. 成功后只追加 `tool_result`：不重新显示已解决失败，也不调用 AI；追加可输入消息后，按正常增量整理规则处理。
5. 从未成功的真实失败不能仅因数据缺失或当前 cutoff 下无输入而冒充已解决；未来时间戳、时区偏移、子会话及 `status=nothing` 的正常成功分别覆盖。
6. GUI 对 `Nothing` 的提示、笔记入口和刷新后的失败数一致，不再把这三个已成功会话显示为仍需重试。
