# 第 8 期：旧备份压缩存放

> 先读 `PLAN.md`（第 4 节"第 8 期约定"、第 6 节通用约束），以及 `P1`、`P5` 的验收文件，了解 `raw/` 是怎么写进去、怎么被读的。
> 遇到 **【检查点】** 必须停下，把产出交给用户转给 leader 审核。
> 结束时版本 `AGENTKB_VERSION = 0.8.0`。

## 1. 为什么做

`~/AgentKB/raw/` 是会话原文件的原样拷贝，不压缩。4 个半月已经 3.6 GB（`codex` 3.2 GB、`claude` 0.4 GB），按这个速度用 3–4 年会到 30–45 GB。这类文本压缩后通常只剩几分之一。

用户的要求：设置页加一项"超过 N 天没有新消息的会话，备份自动压缩"，N 由用户设，可以关闭。

## 2. 现在只做设计（和 Windows 版同时进行）

Windows 那边的执行 AI 正在 `agent-kb-win` 分支上做第 7 期，会改到文件读写、锁、导出、后台进程这些地方，和本期要改的有重叠。所以：

- **这次只做步骤 1：调研、实测、写设计，不改源码**。实测用的脚本可以提交到 `docs/agent-kb/p8-evidence/`
- 实现什么时候开始、哪些文件先改，由 leader 看完两边的设计后再定

## 3. 已经定的事

| 项 | 决定 |
|---|---|
| 压缩什么 | 只压 `raw/` 里的备份。关键词索引、语义索引、笔记都不动 |
| 什么时候压 | 跟着定时收集顺带做，每次限时、低优先级，和建语义索引一样不打扰用户 |
| 对用户的影响 | 搜索结果完全不变；打开旧会话看原文，额外等待不超过 1 秒；Claude Code / Codex 的 resume 用的是它们自己的原文件，不受影响 |
| 安全 | 压缩先写临时文件，校验解压结果和原文件逐字节一致后才替换；中途断电、被杀掉，原文件都还在 |

## 4. 步骤 1：设计说明 `docs/agent-kb/P8-design.md` 【检查点】

每一条都写出依据的文件和函数：

1. **现在谁在读 `raw/`**：列全。至少有收集（追加写入、按字节位置续读）、建索引、`--kb-show`、App 里打开会话、整理（digest）、建语义索引、P5 导出导入、换数据目录、移动硬盘备份。每一处压缩后怎么办
2. **字节位置的问题**：`messages.byte_off` 等字段记的是原文件里的字节位置（`db.rs`、`index/messages.rs`、`search.rs` 用到）。压缩后这些位置怎么用：例如整份解压后再按位置读、分块压缩（可随机访问的 zstd 帧）、或者别的办法。比较后给出选择
3. **什么样的会话算"旧"**：按最后一条消息的时间，还是按文件最后修改时间；压缩后的会话如果又有新消息（用户 resume 了一个旧会话）怎么办
4. **实测**（在临时 HOME 里，对真实 `~/AgentKB` 的副本，只读真实数据）：
   - 用设计选定的压缩方式和级别，全部 `raw/` 压完后多大、压缩一遍要多久、峰值内存多少
   - 解压最大的几个会话各要多久（列出文件大小）
   - 按 30、90、180 天三个门槛，各能压掉多少空间
5. **设置页草图**：开关、天数、"已压缩 X 个会话，省下 Y GB"、"现在压缩一遍"
6. **和别的功能的关系**：P5 导出导入（导出文件里存压缩的还是解压的，旧版 0.6.x 能不能读）、换数据目录、移动硬盘备份（备份到 U 盘的是压缩的还是原样的）、`--kb-reindex`
7. **默认值建议**：默认开还是关，N 默认多少，理由
8. **改动清单和新依赖**（`zstd` 已经在 P5 用了）；**和 Windows 版可能冲突的文件**单独列出来
9. **风险和要 leader 决定的事**

写完提交并推送到 `origin/agent-kb`，然后**停下**等审核。
