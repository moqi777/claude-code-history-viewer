# 第 4 期：每日整理成笔记

> 先读 `PLAN.md`（特别是第 4 节"第 4 期整理规则"，那是和用户确认过的）、`P3-acceptance.md`、`P3.1-acceptance.md`。PLAN 第 3 节的架构决定、第 6 节的通用约束都适用。
> 遇到 **【检查点】** 必须停下，把产出交给用户转给 leader 审核，通过后才能继续。
> 版本 `AGENTKB_VERSION = 0.4.0`。

## 1. 本期目标

做完后：

1. 每天到了整理时间，后台自动调用本机的 `claude -p` 或 `codex exec`，把这一轮聊过的会话提炼成笔记：**遇到了什么问题、原因、怎么解决的、结论**，每条都能点回原会话的那几条消息
2. 电脑关机、睡眠、额度用完都不会漏：下次定时检查时自动补跑，只补没做完的
3. App 里能看笔记、能手动"整理全部未整理的""立即整理这个"；Agent 用 `--kb-search` 查历史时，笔记排在原始消息前面
4. 用户自己日常用 Claude、Codex 时完全无感：不额外调用 AI，不弹窗，不占用他正在用的会话

## 2. 范围

**要做：** 整理任务（`--kb-digest`）、轮次和完结标识、补跑与重试、互斥、笔记存储和索引、App 里的笔记页面和手动按钮、设置项（用哪个 AI、模型、整理时间、费用上限）、`--kb-search` 返回笔记、skill 模板 v3、P3.1 第 4 节的 3 条待办。

**不做：** 语义搜索（第 6 期）、导出迁移（第 5 期，但本期的存储方式要让它好做）、跨会话合并成主题文章、Windows。

## 3. leader 已定的事

| 项 | 决定 |
|---|---|
| 笔记以文件为准 | 笔记由 AI 生成，不能从 `raw/` 重建，所以**和 raw 一样是可信来源**：每个会话一个文件，放 `~/AgentKB/notes/<source>/<session_id>.json`（原子写入）。`kb.db` 里的笔记表和索引只是派生数据，`--kb-reindex` 要能从 `notes/` 重建。移动硬盘备份要把 `notes/` 一起带上 |
| 笔记的形状 | 一个会话一份笔记，里面 0～N 条知识条目。每条至少有：标题、问题、原因、解决办法/结论、关键词、出处（会话 id + 消息 seq 范围）、整理时间、用的哪个 AI 和模型、属于哪一轮。没有值得记的内容就记"无可提炼"，同样算"已整理" |
| 跨轮次 | 同一会话在下一轮有新内容时，只把**新消息**加上**上一版笔记**发给 AI，让它更新这份笔记，不要重发整个会话 |
| 发什么给 AI | 从索引里取（已经脱敏过），不读 raw 原文；思考过程、大段文件内容、图片不发；`--kb-search`/`--kb-show` 的调用和结果不发。发送前再过一次 `kb/redact.rs`。单次输入要有上限，超长会话怎么切由你在设计里定，并用真实数据说明依据 |
| 哪些会话不整理 | 子会话（并进父会话一起整理）、被"排除的工作目录"命中的、整理任务自己产生的会话、消息太少的（阈值你定） |
| 首次整理的范围 | 库里已有 300 多个历史会话，一次全整理费用不可控。**自动整理只处理最近 7 天有活动的会话**；更早的只能手动点"整理全部未整理的"，点之前先显示"预计 N 个会话、约 X 万 token"，用户确认后才跑 |
| 费用上限 | 设置里有"每轮最多整理 N 个会话"（默认 30）。到上限就停，剩下的留到下一轮，不算失败 |
| 调用 AI 的隔离 | 在专用目录（例如 `~/AgentKB/digest-work/`）里运行，这个目录**在代码里固定排除**，不依赖用户的排除设置。关掉 AI 的文件读写、命令执行、联网工具和 MCP；不加载用户的 CLAUDE.md、skill（否则会调到 agentkb 自己）。具体用哪些参数，必须在本机实测后写进设计 |
| 不污染源目录 | 整理时调用的 `claude`/`codex` 如果会在 `~/.claude`、`~/.codex` 里留下会话文件，优先用它们自带的"不保存会话"参数；做不到的，要保证这些会话落在专用目录对应的项目下并被排除。这一点要实测，写清楚会留下什么 |
| 定时 | 不新增 launchd 任务。现有的 `--kb-sync` 每次跑完后检查有没有到期、没完结的轮次，有就**另起一个后台进程**跑 `--kb-digest`，不能让收集等整理 |
| 互斥 | 整理用单独的锁，和收集的锁分开。手动按钮和自动任务抢同一把锁，抢不到就提示"正在整理中" |
| 默认用哪个 AI | 向导和设置里选 Claude 或 Codex，以及模型（可以留空，用 CLI 自己的默认值）。有"测试"按钮：真调一次，显示用时和 token。没装、没登录的要给出明确提示 |
| 失败处理 | 按 PLAN 的规则：额度不足 1 小时后再试；其他失败最多重试 3 次，然后在 App 首页提示是哪个会话、什么错误。怎么判断"额度不足"要实测两个 CLI 的真实报错 |

## 4. 执行步骤

### 步骤 1：写设计说明 `docs/agent-kb/P4-design.md` 【检查点】

每一条都写出依据的文件和函数，涉及 CLI 行为的写出实测的命令和输出：

1. **表结构和文件格式**：笔记 JSON 的完整示例；`kb.db` 里的轮次表、会话整理状态表、笔记表、笔记的 FTS；和 `sessions`、`messages` 的关系；schema 怎么升级
2. **轮次**：整理时间点怎么配（默认凌晨 3 点？你给建议）；"一轮"的边界怎么算；跨天会话的新内容怎么归到下一轮；"30 分钟内有新消息先跳过"怎么判断；什么时候给会话打"已整理"、给这一轮打"完结"
3. **补跑**：关机一整晚、睡眠、中途额度用完这三种情况，分别走一遍时间线，说明下次检查时会做什么
4. **发给 AI 的内容**：取哪些消息、怎么拼、长度上限和超长会话怎么切；给出提示词全文；要求 AI 输出 JSON，怎么校验，不合格怎么办
5. **调用参数实测**：`claude -p` 和 `codex exec` 各自的完整命令；怎么关掉工具、MCP、用户配置；会不会在 `~/.claude`、`~/.codex` 里留文件；额度不足时的真实报错是什么样；怎么拿到这次用了多少 token
6. **用真实数据量出来的数字**：在临时 HOME 里，对真实库副本挑 5 个大小不同的会话（含一个 1000 条以上的）真跑一次，给出每个会话的输入 token、输出 token、用时。据此估算"每天平均一轮"大概多少 token
7. **互斥和后台进程**：两把锁怎么配合；`--kb-sync` 怎么拉起 `--kb-digest`；App 退出、进程被杀时锁怎么释放
8. **搜索和 skill**：笔记怎么进 `--kb-search` 的结果（输出里怎么区分笔记和原始消息，排序怎么定）；SKILL.md v3 的改动全文
9. **界面草图**：首页的整理状态（上一轮时间、是否完结、待整理数、失败提示）、笔记列表、会话里的笔记面板、两个手动按钮、设置项、向导里新增的一页
10. **改动清单和新依赖**

写完提交并推送，然后**停下**，等待审核。

### 步骤 2：整理任务、存储、补跑

按设计实现。测试时用一个**假的 AI 命令**（脚本，按参数返回固定 JSON、模拟超时、模拟额度不足），不要每次都真调 AI。

### 步骤 3：界面和 skill

笔记页面、手动按钮、设置和向导、首页状态、skill 模板 v3。

### 步骤 4：小样本真跑 【检查点】

在临时 HOME 里，对真实库副本选 **10 个会话**（leader 建议：WindowServer 内存那次、充电功率那次、P1 设计那次，再加 7 个你挑的，类型尽量不同）真跑整理，把 10 份笔记原文贴进 `docs/agent-kb/P4-samples.md`，每份旁边写上原会话标题和 resume 命令，方便用户对照。**停下**，等用户和 leader 看完笔记质量再继续。

### 步骤 5：顺手修 P3.1 的 3 条待办

见 `P3.1-acceptance.md` 第 4 节：跳转后高亮命中消息；顶部 ⌘K 搜索和知识库搜索容易混淆（改成走知识库搜索，或者改名区分，你在设计里给方案）；状态栏没选项目时显示"会话：0个"。

## 5. 验收标准

**执行 AI 自己验证（报告里贴命令和输出，全部在临时 HOME 里，用假 AI 命令和假时钟）：**

1. **关机一整晚**：整理时间点过了、期间一次都没检查，下一次检查后 1 小时内这一轮完结
2. **额度用完**：整理到一半返回额度不足，1 小时内不再调用；恢复后只整理剩下的会话，已整理的一个都不重调
3. **互斥**：自动整理进行中点"整理全部未整理的"，提示正在整理，假 AI 命令的调用次数没有重复
4. **其他失败**：同一个会话连续失败 3 次后不再重试，首页显示提示
5. **跳过规则**：30 分钟内有新消息的、子会话、被排除的、整理任务自己产生的会话，都不会被单独整理
6. **跨轮次**：同一会话第二轮只发了新消息和上一版笔记（看假 AI 收到的输入）
7. **重建**：删掉 `kb.db` 里的笔记表后 `--kb-reindex`，笔记全部恢复，搜索结果一致
8. **不碰源目录**：整理前后对 `~/.claude`、`~/.codex` 拍快照对比，除了设计里写明的以外没有任何变化
9. **不影响收集**：整理在跑时，`--kb-sync` 照常完成，用时不受影响
10. **发送前脱敏**：在假 AI 收到的输入里查不到测试用的假密钥
11. 一次 `--kb-search` 仍然 ≤ 300ms；PLAN 第 6 节的全部检查通过；写好 `docs/agent-kb/P4-report.md`，推送到 `origin/agent-kb`

**用户真机确认（报告最后单独列出清单）：**

12. 设置里选好 AI，点"测试"能通过
13. 第二天早上打开 App，首页显示上一轮已完结，能看到昨天会话的笔记
14. 在 Claude Code 或 Codex 里问一个昨天聊过的问题，回答里用到了笔记

## 6. 注意

- 用户的 `~/AgentKB` 里有真实数据。第一次在真实库上升级 schema 之前先备份 `kb.db`；**不要在真实库上自动整理**，真机开启由用户在设置里自己打开
- 真调 AI 会花用户的额度：设计阶段和步骤 4 合计不超过 **30 次**真实调用，报告里列出每次的用途和 token
- 测试不能往真实的 `~/.claude/skills`、`~/.codex/skills` 里装东西，不能改用户的 `config.json`
- 遇到本文件没有覆盖、而且会影响设计的情况，先停下来提问
