# 第 7.3 期报告：从硬盘恢复

版本 `0.7.3`（`mod.rs`、`branding.ts`）。打好的包：`src-tauri/target/release/bundle/macos/AgentKB.app`（ad-hoc 签名，`codesign --verify --deep --strict` 通过；主程序 `Contents/MacOS/AgentKB` SHA-256 `c460b7c5359d67552f6326beaa12432a8397d69f66bf6d151d32f21d071def6a`，61,564,480 字节）。**没有安装到 /Applications，没有在真实数据上点过恢复。**

## 1. 界面

设置页"移动硬盘"那一栏下面新增"从备份硬盘恢复"，按钮"从硬盘恢复…"（`KbRestore.tsx`）。点开是一个对话框：

1. 选文件夹：已设置硬盘时，第一个按钮直接是"使用 `<硬盘>/AgentKB-backup`"，另有"选择其他文件夹…"（系统选择器，起始位置是已设置的备份文件夹）；没设置硬盘时只有后者
2. 检查：页面里显示会话数、笔记数、备份文件数和大小、快照时间；说明"现在的数据（N 个会话、M 条笔记）会先移到数据文件夹里的 `before-restore-<时间>`，不会删除"；磁盘空间不够时按钮置灰。**点"恢复"之前不会动任何东西**，没有用 `window.confirm`
3. 恢复中：进度（检查数据库 → 复制 n/m 个文件、字节和百分比 → 补齐索引 → 替换数据），可取消（替换那一步开始之后不能取消）
4. 完成：提示"语义搜索要重新设置"（按钮"前往语义搜索设置"，滚动到设置页里的语义那一栏）；"建议立即收集"（按钮"立即收集"）；原数据所在的路径；快照之后补回了几个会话；有几个会话没有备份文件
5. 失败：按错误码显示一句话，并写明数据有没有变；"重新开始"回到第 1 步

5 种语言全部翻译（`kb.restore.*`，含各错误码），`i18n:validate` 通过。命令是桌面端专用（`kb_restore_inspect`、`kb_restore_start`，和导出导入同一处注册，同一个"一次只做一件事"的槽位和取消开关）。

## 2. 后端（`restore.rs`）

**检查 `inspect`（只看，不改）**：要求有 `kb.db` 和 `raw/`；备份文件夹不能在数据文件夹里面（`bad_source`）。`kb.db` 先拷到本机 `.restore-look-<pid>/`（边拷边算 SHA-256，拷完回读核对），**在本机副本上**用只读方式打开，不迁移；`integrity_check` 不是 ok → `corrupt`；`user_version` 比当前程序新 → `too_new`；缺 `files`/`sessions` 表 → `corrupt`；比当前旧 → 照常迁移，界面提示"恢复时会升级"。硬盘上不用 SQLite 打开任何东西。

**恢复 `restore`**：
1. 先拿锁，**不等待**：`kb.lock`、`digest.lock`、`vectors/embed.lock`，拿不到分别返回 `busy` / `digest_running` / `embed_running`（定时收集、整理、建索引都不会在恢复期间跑）
2. 在 `<数据目录>/.restore-<时间>/` 里准备全部内容：`kb.db` 拷贝并核对；`raw/`、`notes/` 逐个拷贝，跳过路径里任何一段以 `._` 开头的文件（exFAT 伴生文件），逐个核对大小和 SHA-256；空间检查（需要约 110%）
3. 在工作目录里把数据库迁到当前版本、补齐（见 §3）、`notes::reconcile` 按笔记文件重建笔记索引、`journal_mode=DELETE` 收成单文件
4. 全部就绪才替换：现有的 `kb.db`（连同 `-wal`、`-shm`）、`raw/`、`notes/`、`vectors/` 里的内容（`embed.lock` 除外，它是锁文件，留在原地）逐个 `rename` 进 `before-restore-<时间>/`，再把新的 `raw/`、`notes/`、`kb.db`（最后）`rename` 进来。`models/`、`logs/`、`config.json` 不动
5. 第 4 步之前任何失败（包括取消）：现有数据不变，工作目录自动删除。第 4 步中途失败：所有已做的 `rename` 按相反顺序撤销，恢复原样；撤销本身失败时错误信息会写明东西留在哪
6. 恢复后 `vectors/` 里除锁文件外是空的 → 语义状态显示"需要重建"（语义状态本来就只看向量文件，没有记在 `kb.db` 里）

## 3. 第 6 点：快照之后追加的内容怎么处理

这是真实会出现的情况，不是假设：用真实硬盘备份演练时，**4 个文件的备份比快照里记的游标长（共 23,419,032 字节）**，原因就是快照每天一份、`raw/` 每次都追加。

- 同一台电脑、源文件还在：原有收集逻辑本来就对（append 时把镜像截回游标再从源文件续拷），不重复。
- 但源文件不在了（换电脑）或已经被清理：游标之后的内容永远不会被收集，也就搜不到。**恢复时补上**：新增 `sync::index_mirror_tail`，对每个普通镜像，如果文件比游标长，就从镜像里读游标之后的完整行，建索引，把 `mirror_offset`/`head_hash` 推到最后一个完整行的末尾。源文件那几列（大小、mtime）不动，所以以后源文件还在时，收集会从新游标继续追加，既不漏也不重复。最后一行不完整的字节留在镜像里，下一次追加会从游标截断重拷。
- **换了电脑、换了用户名/源文件夹**：快照里记的 `source_path` 是旧电脑的路径，而 `mirror_rel` 是由源文件相对路径决定的，新电脑收集时会得到同一个 `mirror_rel`、不同的 `source_path`，插入时报 `UNIQUE constraint failed: files.mirror_rel`（测试里先复现了这个错误）。恢复时按 `discover.rs` 的规则（`claude/projects/…`、`codex/<子目录>/…`）把每个文件的 `source_path` 改成这台电脑上的位置（报告里的 `rehomed_files`）。没有配置的来源保持原样。
- 备份里有、数据库里没有的文件（不会发生，数据库是快照之前的）不处理；**数据库里有、备份里没有的文件**只计数（`missing_files`），界面提示"文字能搜到、原文件打不开"。典型成因：快照里记的是 Codex 的 `.jsonl`，之后被压成 `.zst`，硬盘上的明文又被 P8a 的清理删掉。本期没有做自动改指到 `.zst`。
- 笔记：`notes/` 里的文件是笔记的权威来源（笔记会就地修改），恢复时重建索引，所以快照之后改的笔记也在。

## 4. 测试

`restore.rs` 12 个单元测试，全在临时目录里；另有 1 个手动的 `#[ignore]` 测试（`restore_a_real_backup`，见 §5）。

- 正常恢复后能搜到、能打开、`raw/` 逐字节一致、`._` 文件不在；没有 `.restore-*` 残留
- 已有数据时：原数据逐个文件按 SHA-256 完整地进了 `before-restore-*`；`vectors/` 里的向量文件被清走但锁文件还在；`models/` 不动
- 缺 `kb.db`、`kb.db` 损坏、缺 `raw/`：拒绝，现有数据（逐文件哈希）不变，无残留
- 快照来自更新的程序（`user_version=99`）：`inspect` 和 `restore` 都拒绝（`too_new`）
- 备份文件夹在数据文件夹里面：拒绝
- 拷到一半失败（一个备份文件不可读，仅 unix）：现有数据不变、无工作目录残留、没有生成 `before-restore-*`
- 三把锁分别被占用：各自返回对应错误，耗时不到 5 秒（不等待），数据不变；释放后可以恢复
- 替换中途失败（在"挪开旧数据后"、"raw 就位后"、"notes 就位后"三个点注入）：全部撤销，目录哈希和原来一致
- 快照之后增长的文件：恢复后索引里就是完整的消息数；再用同一份源文件收集一次无错误、不重复；源文件再追加后收集，消息数和镜像内容都对
- 恢复后没有源文件时收集：无错误，第二次收集 `changed_files = 0`
- 数据库有而备份缺的文件：计数
- 前端 `KbRestore.test.tsx` 8 个：确认前不会开始（只检查）、按确认后以检查过的那个文件夹开始、没设置硬盘时手动选、取消选择器什么都不做、完成后有语义设置和"立即收集"的提示、被拒绝时显示原因、失败时确认按钮消失、空间不足时按钮置灰

7 项检查：tsc 通过；vitest 148 个文件 / 1585 通过；lint 通过；i18n:validate 通过；`cargo test -- --test-threads=1` 1509 通过、8 忽略；clippy 通过；fmt 通过。

## 6. 需要知道的

- 没有在真实 `~/AgentKB` 上恢复。Mac 上 `/Volumes/Share` 当前是挂着的，演练只读它。
- **同一台机器上恢复到"当前比备份新"的库**：现有数据整体挪进 `before-restore-*`，比备份新的部分只在那里。恢复后立即"立即收集"能把还在源目录里的补回，但已被 Claude/Codex 清理掉、又不在备份里的就只在 `before-restore-*` 里。界面文案已写明现有数据只是被挪开。
- 恢复期间不能取消的只有最后的替换（几次 `rename`）。Windows 上若数据库文件被别的进程打开，`rename` 会失败，此时会整体撤销并报错，数据不变；没有在 Windows 上跑过（和 P7 其它部分一样，需要在 Windows 上验）。
- 不恢复：设置（`config.json`）、`models/`（留在原地）、日志、语义索引。恢复后需要重新走设置（若是新电脑），并重新建语义索引。
- 用户名不同时，Claude 的项目目录名里编码了旧用户名的路径（`-Users-old-proj`），新电脑上的新会话文件会在另一个目录下，不会和旧记录重复，但同一个会话如果在两台电脑上都有，会出现两份。这属于导出/导入（P5）的合并问题，不在本期范围。
- 硬盘上 `kb.db` 是上次快照；恢复不会修改硬盘上的任何东西。
