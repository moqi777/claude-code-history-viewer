## 3. 临时 HOME 下的恢复与双机备份

### 3.0 首轮检查发现并修复的 Windows 差异

首轮 Rust 库测试为 1,494 通过、1 失败、9 忽略。失败是既有正常恢复测试：空目标库恢复后应没有 `set_aside`，Windows 却返回了 `before-restore-*`。

原因是 `SyncLock` 在 Windows 使用 `.embed.lock.info` 辅助读取持锁诊断；`restore::vector_entries` 原来只排除 `embed.lock`，把该诊断文件当成向量索引移走，导致空库也报告保留旧数据，并使诊断文件脱离原锁路径。修复为 Windows 同时排除这个准确文件名，Mac 的文件筛选行为保持原样；未放宽原测试断言。另加断言确认恢复后旧数据目录及当前向量目录都没有残留诊断文件。最终结果见 §2。

复跑中新增的“失败位置正是被占用文件”断言因正反斜杠混用误报；错误消息实际指向同一个向量文件（Windows 错误 32）。断言统一分隔符后再比较完整路径。首轮及该次复跑日志分别保留为 `check-cargo-before-fix.log` 和 `check-cargo-path-assertion.log`，最终结果为 `check-cargo.log`。

本机 Rust 1.99.1 / clippy 0.1.99 还要求把既有的快照时间非空断言写成 `assert_ne!(info.snapshot_at, "")`，已按提示调整（检查条件相同，不屏蔽 lint）。

### 3.1 文件被占用时撤销恢复

新增 Windows 专属回归测试 `windows_open_files_block_restore_and_all_prior_moves_are_undone`。用真正的 Windows 打开文件句柄（允许读写共享、不允许删除共享）分别占用 `kb.db`、`notes/held.json`、`vectors/model.sqlite3`，不使用模拟失败注入。

向量文件在交换顺序最后面，因此它被占用时，旧数据库、raw 和 notes 已被移走；测试要求操作失败后全部退回。逐文件 SHA-256 比较恢复前后数据（日志与锁文件除外）、备份、模拟来源文件；要求没有 `.restore-*` 临时文件残留、旧库仍可查询。释放句柄后再次恢复，要求能读到备份中的消息、保留旧数据到 `before-restore-*`、清空旧向量索引且保留模型文件。

**通过，三个占用位置均验证成功**。最终代码对应日志为 `D:/AgentKB-build/tmp/agentkb-p74-home-3d74cpap/restore.log`，每个位置都输出 `rollback intact; restore after release passed`。
